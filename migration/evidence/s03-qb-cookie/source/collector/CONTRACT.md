## Recording layer and finite cases

17 synthetic scenarios / 18 complete original add calls. Inputs contain only owned `.invalid` URL/Cookie values, one relative no-host input and one synthetic magnet. No user/site data is read. The second call in the final scenario keeps the same constructed original instance and recording cookie store.

Four outer qB protocol methods are recording ports: `app_web_api_version`, `app_cookies`, `app_set_cookies`, `torrents_add`. Inputs specify their replies or an owned RuntimeError, never an expected original output. Capture includes ordered calls/kwargs/returns/exceptions, original WARN/ERROR logs, tuple/type/truthiness, and cookie store before/after/final. The successful recording set deep-copies its input into an owned in-memory store; an injected set error is explicitly pre-effect. **Neither is evidence of actual daemon storage/error atomicity.** A subsequent add error cannot rewrite that recorded history.

Cases cover threshold/below/rc/local/invalid/null/query-error versions; ordinary JSON existing entries with duplicate identity, default/other path, dotted/other domain, dropped absent values and expiration zero; empty store; no morsels/invalid Cookie/no hostname; read/set exceptions; add false/error after successful write; magnet bypass; and sequential merging. General arbitrary getter objects, vendor Cookie/List model semantics, unconstrained Python values and full SimpleCookie/PEP440 domain remain beyond these finite observations.

Existing vendor sources show that app_cookies/app_set_cookies have their own version gates and may cause additional version reads. Thus **outer protocol call counts are not HTTP request counts**. No vendor HTTP authentication, escaping/form serialization, retries, cookie daemon behavior, real downloads, SDK/host/full AddTorrent or full S03 equivalence is claimed by this collector.
