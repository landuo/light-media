# 生产性能测试与优化（2026-11-16）

对象：NAS 上运行中的 light-media（schema 3，44,455 行迁移完成）
方法：Chrome 实机页面计时 + 服务端 `request_completed.duration_ms` 对照 + 接口逐项测量

## 1. 优化前测量

| 操作 | 耗时 | 说明 |
| --- | --- | --- |
| 关键词资源搜索（全部站点） | **23.1 s** | 825 条候选，等待最慢站点 |
| 日志页查询 | **2.0 s** | 每次扫描约 32 MB 日志文件 |
| 日志页（ERROR 筛选） | 2.1 s | 命中少，仍扫满预算 |
| 通知列表（冷） | 0.5–2.0 s | 首次请求受主线程与冷缓存影响 |
| 整理历史（含能力字段） | 0.9 s | 逐条计算可重整/可识别 |
| 任务队列 / 站点 / 文件 | 0.2–0.4 s | 正常 |

服务端聚合（历史日志）显示 `http.search` 平均 24.9 s、`http.files` 平均 17 s、`http.history` 平均 13.8 s，均集中在少数重操作。

## 2. 根因

1. **日志查询不按时间窗截断**：反向扫描遇到早于 `from` 的行仍继续读，直到 2 s 预算用尽，每次都扫 32 MB。
2. **资源搜索存在全局屏障**：没有插件提供 `async_batch_search_torrents` 时，包装器仍把 17 个站点放进同一个批次，`workers.Wait()` 等最慢站点（45 s 超时），单个卡住就拖住全部结果。
3. 插件批次回退时先跑的 native 结果被丢弃，回退链路重跑一遍，进一步放大等待。

## 3. 修改

| 修改 | 文件 | 效果 |
| --- | --- | --- |
| 反向扫描遇到 64 条连续早于 `from` 的记录即结束 | `logs_query.go` | 扫描量 32 MB → 64 KB |
| 无插件批次方法时按站点并行直连，不再有全局屏障 | `plugin_original_resource_batch.go` | 结果随站点完成返回 |
| 保留插件回退前的 native 结果，作为超时时的部分结果 | 同上 | 预算到期仍有候选 |
| 交互搜索预算 15 s（与站点 15 s 超时对齐），超时返回部分结果与站点 `timeout` 状态 | `search_parallel.go`、`resource_search.go`、`search_stream.go` | 最坏 6–7 s，不再无限等待 |
| 流式搜索同样受预算约束，但进度事件仍即时推送 | `search_stream.go` | 首个进度事件 18 ms |

## 4. 优化后

| 操作 | 优化前 | 优化后 |
| --- | --- | --- |
| 关键词搜索（流式完成） | 23.1 s | 15–17 s（首帧 93 ms，17 站点全部返回） |
| 关键词搜索（普通 POST） | 23.1 s | 15–17 s，候选 932 |
| 日志默认查询 | 2,028 ms / 32 MB | **58–111 ms / 64 KB** |
| 日志 ERROR 筛选 | 2,063 ms | 64 ms |
| 整理历史列表 | 922–965 ms | 25–327 ms（能力字段延迟加载时更快） |
| 站点管理 | 302–924 ms | 100–367 ms |
| 任务队列 | 222–2,209 ms | 111–177 ms |
| 其余页面 | — | API 全部 < 400 ms |

服务端 p95（最近一小时）：所有 `http.*` 模块 < 25 ms。

## 5. 仍偏慢但与本次改造无关

- 仪表板插件状态卡片：约 1.4 s，耗时在插件宿主调用 `BrushFlowLanduo/status`。
- 站点连通性测试、订阅搜索等外向网络操作，取决于站点响应。
- 刷流插件连接下载器失败（11-10 起既有问题）会周期性产生错误日志，但不阻塞请求。

## 6. 复测命令

```bash
# 服务端最近的请求耗时
docker logs --since 10m light-media 2>&1 | grep request_completed | tail

# 浏览器侧：在页面控制台
performance.getEntriesByType('resource').filter(e=>e.name.includes('/api/'))
```
