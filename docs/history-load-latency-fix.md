# 整理历史列表：避免读取记录时扫描 NAS 文件树

## 问题与修复

整理历史接口原来在数据库分页完成后，对每条记录同步运行执行能力检查。
检查会读取源路径；目录会递归读取全部成员、排序并生成目录快照（最多 20,000 个成员）。
失败记录的重试检查还可能再次生成快照。NAS 慢盘或不可用的挂载可能使整个列表等待；
请求的 context 截止不能中断正在阻塞的文件系统调用。页面存在 pending 记录时每 3 秒刷新，
因此不应把操作前的文件检查放在列表展示/刷新链路。

前端的所有历史分页请求统一传 `capabilities=deferred`：

- 列表只读取持久历史，不再为每一行扫描源目录或检查重试执行条件。
- 返回 `capabilities_deferred: true`，`can_retry` 和 `can_recognize` 保守置为 false，不能误认为已验证。
- 页面并不按这两个能力字段禁用按钮，单行和批量重新整理、删除入口仍可用。
- 未传参数的旧 API 客户端保持原有检查行为；单条详情及真实操作不接受此参数绕过检查。
- 重新整理仍重新解析当前历史、核对执行文件/快照，删除和重试仍进行原来的严格检查。

## 验证范围

新增后端回归覆盖：缺失源的列表显示、后续刷新、深目录无法建立快照时的历史显示、旧接口兼容、
单条详情严格检查、传 deferred 参数也不能重试缺失源。
前端回归覆盖搜索、状态筛选、翻页和全部页大小均使用同一 deferred 查询。

这些是本地合成数据与自动化验证，不能代替 NAS 日志和实际部署验证。
首次历史索引构建、数据库锁竞争、NAS 硬件/挂载故障仍需按实际日志单独排查。

## 本次本地结果

- 前端 604 项测试通过（日志 oracle 要求 UTC+8，使用 `TZ=Asia/Shanghai`）。
- 前端构建与 TypeScript 检查通过，嵌入静态资源测试通过。
- 后端历史相关 race 回归 62 个测试/子场景通过，无跳过；163 个包编译检查通过。
- 本地合成目录 benchmark：同一页 50 条目录历史、合计 3,200 个成员，预热索引后每组 3 次：
  旧同步检查约 32.15 ms/次、4.75 MB 分配；deferred 约 5.38 ms/次、0.37 MB 分配。
  这是本地快速磁盘数据，不代表 NAS 的绝对耗时；主要收益是列表不再依赖源文件系统响应。
- 未执行真实浏览器或 NAS 部署验证，也未声称已复现 NAS 上的具体报错。
