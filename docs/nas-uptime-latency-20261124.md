## 登录和设置为何能一起超时

1. 上午旧进程 92 个已记录的登录状态请求里，43 个未取得 HTTP 状态；设置为 30/47。进程 RSS 采样约 121.5–135.6 MB，同窗口资源组 high 事件增加 552,652，OOM 增量为零。旧进程 10:20 的另一份读数为累计 167,706 次 GC，强制 GC 为零，活堆 57,869,800 字节，Go 运行时内存软目标为 58,720,256 字节。两者之间还要容纳栈和其他 Go 运行时开销。高频回收和代码缺页会拖慢最小请求。Go 的内存目标与 Linux 的进程组预算分别计量。[Go GC 指南](https://go.dev/doc/gc-guide) [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)
2. 旧进程堆剖面显示，辅种插件的编码识别全局模型长期持有 22 MiB 权重。已声明字符集的常规解码也会触发首次加载。修复后直接使用已声明编码，真正检测时只保存 521,737 个非零权重及其位置，权重数组约 1.49 MiB。回归测试独立验证声明编码路径，以及 352 × 65,536 个权重逐值一致。日志脱敏也改为每条日志只提取一次配置中的敏感值。
3. 在 NAS 上使用独立 Btrfs 测试文件、170 MB 软阈值和相同 24 个离散页做四次冷读。普通预读两轮均读入 52,998,144 字节，耗时 353.5 和 360.0 毫秒。逐页读取均读入 98,304 字节，耗时 7.2 和 5.6 毫秒，四次校验和一致。0.58.26 和 0.58.27 进程的代码段和只读数据段已实测带有 rr 标记。旧机慢现场没有逐请求缺页归因，磁盘耗时与 GC 停顿的占比未知。
4. 旧版登录校验和设置继承项与业务查询共用四个 SQLite 读连接。回归测试占满这四个连接后，直接请求两个正式接口，仍得到有效会话和设置。修复保留逐请求校验过期时间，给这两个短查询预留一个只读连接，页缓存预算 256 KiB。占满预留连接时也验证了请求超时能正常退出。

## 重点页面和业务正确性

刷流详情页仅在请求归档时读取归档，同一次响应复用任务记录和运行历史，只为请求页合并下载器实时进度。状态页按当前记录内容校验做种体积，缓存只存校验值和总数。订阅页面每轮独立核对样本剧集的已下载集数。目录设置存在另一个会影响下载器的缺陷，GET 曾原地清空共享设置快照的密码。已删除这处写入，并通过正式 HTTP 入口回归验证。

目录待处理计数原先扫描 1,466 条目录记录并临时分组，NAS 同类查询实测 189 毫秒。修复后走仅含待处理记录的索引，该次小于 1 毫秒。媒体元数据与插件状态按条目变化失效，站点统计在各站点改变时重读相应站点的原始观测；同域名、多站点、同日错误与成功记录并存都已回归覆盖。

## 针对运行数小时后负载的修复验证
