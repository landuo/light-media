# 插件大消息传输：已证实限制与实现边界

日期：2026-10-16。分块协议已正式接线并通过普通、竞态及 NAS 隔离验证；App 结果保存、启动保护及 4,500 条完整页面已通过本机普通/纯 Go SQLite、相关竞态、网页及本轮 NAS 隔离验证。协议完成不等于任意合法历史均能构树、传输和显示，也不等于插件已迁移。

## 三个独立限制

1. Runner/SDK 保留默认 1 MiB 物理帧，通过协商后的分块承载四个方向的大逻辑消息。调用、宿主反向调用、宿主返回和插件返回都已覆盖实际子进程的完整 16 MiB 值。
2. `FinishRun` 与 `run_result` 原先仍限 1 MiB，本切片改为独立 16 MiB 完整编码值，普通配置/输入限额不随之扩大。结果保存失败的终态和启动行为也须验证，不能据 IPC 成功报告整个执行成功。
3. SubscribeGroup 的 `RawPage` 构造完整组件树。4,500 个空对象的历史 JSON 仅 13,501 字节，完整页面却为 1,121,054 字节；因此只检查历史输入大小不足以避免返回失败。合法 16 MiB KV 的最坏膨胀可远超工作器内存预算，传输分块本身不等于流式页面构造。

SubscribeGroup 的单帧历史预检已移除，直接读取有界完整密文 KV，再由协议分块；未截断数据。小输入展开大页面、输入输出同时跨帧及实际重开后的真实工作器 HTTP 回归已通过。浏览器实际显示 4,500 行、18,000 个单元格并可滚动到第 4,500 条。当前用户原数据较小，不是取消大历史要求的依据。

## 已接线的传输切片

- 保留 1 MiB 物理帧，增加独立的有界逻辑消息层；四个方向统一重组完整原 Frame，再由原严格解码器校验。业务处理器不接收部分 JSON。
- 初次 hello 保持旧字段不变。新 SDK 在握手结果宣告可选能力，新 Runner 再用独立的小消息确认版本与额度，成功后才启用分块。旧 worker 的严格 hello 不能直接加入新字段。
- 内部 `transport.chunk` 使用独立请求 ID/ACK，包含身份、传输 ID、原逻辑 ID/类型、连续序号、总字节数、数据及末块标志。原始约 256 KiB 分块后 base64，实际编码后再次校验物理帧上限。ACK 只确认收块，业务仍须获得原 result/host_result。
- 每方向同时只重组一个消息，不增加多路复用、窗口重传或通用事件系统。SDK 的反向宿主交换串行化，并允许等待锁时取消。
- 独立限制物理帧、完整逻辑字节、双向累计 wire 字节、单消息/会话块数、业务宿主调用数与 deadline；累计额度计入 base64、封套、ACK、握手和停止消息。块数不计作业务宿主调用次数。
- 错序、重复、空块洪泛、身份/逻辑 ID 中途变化、未知传输、错误末块、大小不符、意外 ACK 或未完成 EOF 均停止会话，不执行半条宿主调用。先核验声明大小再分配，实际累计仍逐块检查。
- 真正阻塞的管道依靠进程 context、关闭管道和回收子进程中断；单纯在读写前检查 context 不足以证明取消有效。

正式常量为单值 `MaxPayloadBytes=16 MiB`，完整原 JSON-RPC 帧 `MaxLogicalMessageBytes=16 MiB+4 KiB`。4 KiB 还容纳实际 KV key/value 包装，不能在包装 Payload 上再施加 16 MiB 限制而缩小原合法值。默认单方向累计 wire 为 64 MiB（同方向可能先后承载两份完整值），原始块最多 256 KiB，每消息最多 16,384 块、每方向会话最多 32,768 块。实际 base64、封套、ACK、握手、协商与 stop 全部计费；非默认较小额度可提前拒绝。超额保留完整数据，不能截断后报告成功。

新版 SDK 先在握手结果声明能力，新 Runner 再用独立消息确认额度，原 hello 字段保持不变；旧 peer 沿用旧 wire 和原默认 8 MiB 输出预算。固定旧 codec 只改包名，逐字节核对来自 `ab41d26`，不调用新编解码器。四个文件放在 `internal/plugins/testdata/legacywire/`，仅用于测试。

工作器整份结果若在写任何字节前被逻辑/物理/块额度拒绝，可回传固定安全错误。已部分写入后的失败不能再拼一条普通错误消息。App 只将明确的 `message_limit/frame_limit/input_limit/output_limit/transport_chunk_limit` 映射为页面过大；不把 `incomplete_transport_message/worker_io_failed` 推断成单纯容量问题。失败返回仍保留已完成 HostCalls 和实际 wire/块数证据。

## 应用与验收

App 接线同步处理 `plugin_views.go` 的旧单帧检查、执行结果写入及解密读回。公开执行列表 SQL 不读取大结果，避免为了丢弃 JSON 字段先解密全部结果；输入仅保留提取出的请求关联后释放。结果无法保存时尝试仅写失败状态与发生记录终态，不写坏结果、不覆盖已有终态；若存储连失败状态也写不入，日志明确保留该边界，不能声称已保证阻止所有重放。

结果存储失败会阻止相同安装代际/配置 revision 的新启动初始化；明确保存新配置仍可继续。真实工作器已经调用宿主后发生结果超限、EOF 等普通失败时，保留原错误码，并在同一终态事务写入独立启动保护标记。没有宿主调用的失败不会误加该标记；取消继续沿用具体插件的既有核对路径。测试实际调用 category.write 后超限或 os.Exit，再关闭/重开 App 并执行启动初始化；enabled 仍保持 true，避免依赖分类插件自动清旗而掩盖问题。标记 INSERT 失败的事务回滚和仅状态保存降级也有判别用例。已提交的卸载收据可优先于丢失的工作器回复收尾，不误报自卸载失败。

详情页原来的每层 2,048 / 总 16,384 组件限额会在传输成功后拒绝完整 4,500 行，网页验证发现并修正为详情页独立每层 16,384 / 总 65,536。配置表单仍为每层 256 / 总 4,096，深度仍限 16，组件和事件/HTML白名单未放宽；超过页面上限明确报错，不截断历史。原版页面、四列表格与历史顺序保持不变。这仍不是任意 16 MiB 历史的完整展示保证。

正式协议普通测试通过 10.737 秒，`plugins/...` 竞态通过（主包 143.030 秒），包含四向 2 MiB/16 MiB、4 KiB 小帧、固定旧 wire 双向兼容、错序/身份/长度/ACK/重放/截断、累计额度、并发/晚到调用、阻塞写/缺 ACK/等待门取消与子进程回收。NAS Alpine 3.22 的 UID 1000/GID 1001、无外网、只读挂载、256 MiB 内存、128 MiB tmpfs 及 GOMEMLIMIT=64MiB 环境执行协议全集终态 PASS，包含最大值四向过程。测试程序本机/NAS SHA 均为 `3620a7a241fdc8b4c3731cb33f21736a668269e707a99d8faef57fe907748a30`；独占容器和目录已清理。

最终 App 普通与 modernconly 全集通过，插件/订阅规则相关 App 竞态通过 449.580 秒；前端 124 项测试和构建通过。本轮最终 App 程序在同等 NAS 约束下通过 156 个相关顶层测试，无跳过，包含完整大历史 HTTP、结果保存失败、超限/实际 EOF 后启动保护、事务回滚和卸载收据；不是 NAS 全 App 测试。该程序 SHA-256 为 `6078e252486435be37ff66db0e650fed76848d18363fc50a941a5ffc3cedb022`，本机/远程一致，退出码 0 且未 OOM；测试容器和目录已清理。具体正则与边界见 [卸载宿主验证](plugin-uninstall-go-port.md)。
