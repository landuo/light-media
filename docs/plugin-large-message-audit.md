# 插件大消息传输：已证实限制与实现边界

日期：2026-10-16。本文件是后续实现依据，尚未实现分块协议。不能把下列设计当作已通过的功能。

## 三个独立限制

1. `internal/plugins/{protocol,worker,jsonrpc}.go` 的 Runner/SDK 共用单帧约束。调用、宿主反向调用、宿主返回和插件返回四个方向都可能超过 1 MiB。
2. `plugin_runs.go` 的 `FinishRun` 和 `plugin_store.go` 的 `run_result` 读回仍限 1 MiB。仅修 IPC 会使大执行结果保存失败，不能据此报告成功或永久留在 running。
3. SubscribeGroup 的 `RawPage` 构造完整组件树。4,500 个空对象的历史 JSON 仅 13,501 字节，完整页面却为 1,121,054 字节；因此只检查历史输入大小不足以避免返回失败。合法 16 MiB KV 的最坏膨胀可远超工作器内存预算，传输分块本身不等于流式页面构造。

当前 SubscribeGroup 对超过单帧输入明确返回 `PLUGIN_HISTORY_TOO_LARGE`；页面展开超过单帧也会明确失败，原 KV 不变。该行为保留数据，但不满足完整历史展示要求，仍在原定范围内。当前用户原数据较小，不是取消此要求的依据。

## 最小传输切片

- 保留 1 MiB 物理帧，增加独立的有界逻辑消息层；四个方向统一重组完整原 Frame，再由原严格解码器校验。业务处理器不接收部分 JSON。
- 初次 hello 保持旧字段不变。新 SDK 在握手结果宣告可选能力，新 Runner 再用独立的小消息确认版本与额度，成功后才启用分块。旧 worker 的严格 hello 不能直接加入新字段。
- 内部 `transport.chunk` 使用独立请求 ID/ACK，包含身份、传输 ID、原逻辑 ID/类型、连续序号、总字节数、数据及末块标志。原始约 256 KiB 分块后 base64，实际编码后再次校验物理帧上限。ACK 只确认收块，业务仍须获得原 result/host_result。
- 每方向同时只重组一个消息，不增加多路复用、窗口重传或通用事件系统。SDK 的反向宿主交换串行化，并允许等待锁时取消。
- 独立限制物理帧、完整逻辑字节、双向累计 wire 字节、单消息/会话块数、业务宿主调用数与 deadline；累计额度计入 base64、封套、ACK、握手和停止消息。块数不计作业务宿主调用次数。
- 错序、重复、空块洪泛、身份/逻辑 ID 中途变化、未知传输、错误末块、大小不符、意外 ACK 或未完成 EOF 均停止会话，不执行半条宿主调用。先核验声明大小再分配，实际累计仍逐块检查。
- 真正阻塞的管道依靠进程 context、关闭管道和回收子进程中断；单纯在读写前检查 context 不足以证明取消有效。

逻辑额度需与存储和内存预算共同固定。可先评估 16 MiB 业务载荷加明确封套余量、每方向 32 MiB wire；这些尚未成为运行常量，不能列为当前支持上限。超额必须明确失败并保留全部数据，不能截断后报告成功。

## 应用与验收

传输改造需同步处理 `plugin_views.go` 临时单帧检查、执行结果写入及解密读回、错误终态和已执行宿主副作用的核对。不能因返回或持久化失败就自动重做外部业务。原版页面与历史顺序保持不变。

必要验收：真实 Runner/Serve 子进程四向大消息；完整 4,500 行页面；输入和输出都超一帧的历史；大 invoke 结果加密读回和超额终态；错序/身份/长度/ACK/截断；阻塞写与等待 ACK 取消并回收；固定旧 wire 的双向兼容；非默认小帧和累计额度边界。旧兼容 fixture 不得复用改造后的编解码器。

若要覆盖任意合法 16 MiB 历史，还需继续实现页面/Handler 输出流、组件 JSON 流式生成和 HTTP 返回的端到端资源约束；仅做此传输切片不能称整个存储域均可展示。
